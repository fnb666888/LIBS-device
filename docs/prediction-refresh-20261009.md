# 实时预测显示节奏优化（2026-10-09）

当前激光频率为 1 Hz。真机最近 119 条预测记录的 Python 推理耗时为
234.929～330.035 ms，中位数 247.925 ms；该数值不包含 C++ 请求序列化、
结果文件保存和 UI 显示等待，因此不能用它代表端到端延迟。

发现两个确定的显示问题：

- 预测结果随整机状态线程更新；线程完成 status、param_get、measurement_status
  三次请求后额外等待 800 ms，使显示延迟依赖整机状态请求耗时。
- 后端进入每次推理时清空 latest，UI 会清空数值。轮询落在推理阶段时，只能
  看到“正在预测”，甚至错过一条已经完成的结果。

改为独立 PredictionPoller 工作线程，每轮约 150 ms 请求一次 prediction/status。
该接口只读预测服务的内存缓存，不调用光谱仪 SDK、激光串口或设备状态检查。
相同状态不重复绘制；连接失败降速至约 1 s，保留已有数值并提示连接异常。
整机状态快照不再覆盖预测卡片，避免慢快照倒退到旧结果。

实时推理期间保留上次完成结果，UI 显示“显示帧 N 结果 · 正在计算下一帧”。
完成后替换为新结果。切换模型、关闭预测和提交离线光谱仍清空结果；失败或
不合格结果仍明确显示不可用，不冒充当前帧有效预测。

本次不改变模型、预处理、激光频率、光谱仪 SDK 会话及原始数据保存方式。
150 ms 是轮询目标周期，不是硬性端到端延迟承诺；同一发的预测必然晚于采集。
如以后提高频率，使单帧完整处理耗时超过触发间隔，需要进一步测量并优化推理
吞吐量，或明确选择只预测最新帧的策略。当前仍保留按队列逐帧预测的策略。

验证：后端全部 16 套测试、1939 项检查通过；新增阻塞推理回归测试确保上一帧
结果在计算下一帧期间持续可读，切换配置后旧结果失效。Qt 轮询测试模拟每次
80 ms IPC 和一次连接错误，验证 150 ms 调度、重复状态合并、恢复后重新发布、
工作线程读取及 GUI 事件循环保持响应。真实模型与 Qt 的离线 IPC 验证见构建日志。
