# 持续采集故障的分支对比

参考分支为 `feature/transport-timing-and-preview-cadence`（当前顶端 b472cef，硬件时序修复 5de5adb）。对照对象是 main 当前工作区及真机部署后端，不切换分支、不覆盖既有改动。

## 相同的驱动行为

- USB 初始化均为 `AVS_Init(0)`，同一 SDK 会话只初始化一次。
- 启动时枚举并激活可用通道，复用序列号对应的句柄；采集前读取 SDK 列表，已由本会话持有的设备不会因“应用占用”被拒绝。
- 主机走 Pin 6 外触发，从机走 SYNC 输入，先布防从机、最后布防主机。
- 正向触发时光谱仪的 LASER OUT 宽度和延时都为 0。
- 两边每次 capture 都会执行 StopMeasure、SetSyncMode、PrepareMeasure，再逐发 Measure，轮询 PollScan 并读取 GetScopeData。

因此，逐帧重新配置不是 main 独有行为，不能仅凭 SetSyncMode 报错就认定移植新增的配置步骤是根因。此前将它列为排查重点属于假设，不是已证实结论。

## 业务层的实际差异

| 项目 | 已验证分支 | main 当前实现 |
|---|---|---|
| 持续出光与光谱采集 | LaserFireService 和 SpectrumStream 分开控制 | MeasurementJob 统一管理 |
| 首次开光闸 | 旧有界出光采集路径启动线程后等待 50 ms；连续出光路径单独开启 | 四台 AVS_Measure 成功后回调开光闸 |
| 采集节奏 | SpectrumStream 根据 min_period_ms 扣除本轮耗时后补足间隔；UI 按激光频率推导周期 | 成功帧后直接进行下一次采集，等待外部 TTL；失败重试至少间隔 100 ms |
| 设备访问互斥 | 预览采集持有 device_mutex；一次出光采集用租约排除预览 | 采集持有 acquisition_mutex，激光状态读数使用 device_mutex 和激光驱动内部互斥 |
| 运行期激光状态 | 连续出光与预览各自运行 | 帧间至少间隔 500 ms 重新判定，运行阶段允许正常开启的 Q 开关 |
| 采集异常 | SpectrumStream 发布错误帧并继续循环 | 明确设备缺失立即收光；其他连续三次失败也收光，记录回读结果 |

旧分支的单独预览可选择自由触发或跟随站点外触发；比较真实 LIBS 测量时必须确认启用了跟随触发，不能将背景谱正常返回当作外触发稳定性的证据。旧分支有界多发 capture 在同一次请求内只 prepare 一次，主分支连续测量每次请求一帧；旧分支持续预览每次请求同样是一帧。

## 当前证据与限制

主分支正式 UI 会话成功 28 帧后，第四台 1706100U4 的 SetSyncMode 返回 -16（SDK ERR_COMMUNICATION），随后 SDK 列表缺少该序列号，异常保护收光成功。该会话没有 gate_lost_mid_run 记录。

厂商软件可以识别四台，说明不能根据项目中的 SDK 报错认定硬件损坏。仍需比较相同设备、参数、触发模式和持续时间下的行为，区分 SDK 会话、采集节奏、同步配置和设备访问差异。关闭自动收光只会改变故障后的表现，不能解释或修复此前的通信错误。

用户已授权 120 秒无 UI 测试。首次尝试启动前缺少第四台，未出光、0 帧；厂商软件确认四台并关闭后，继续使用原部署后端和模型测试。具体结果另见采集故障调查记录。

后续测试已完成：运行 120210 ms，采集、保存和预测均为 119 次，采集/保存/预测错误为 0，停止回读成功，设备正常关闭，后端退出码 0。运行期状态检查保持开启。此次未复现 SDK 通信错误，不能据此将 UI 确认为根因，因为新建 SDK 会话及厂商软件访问也改变了试验前状态。
