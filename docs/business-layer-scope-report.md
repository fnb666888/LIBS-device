## 1. 判定标准

一个业务能力能否"现在放入业务层"，取决于三个门。三个门全过 = **A 类**；门没过但**接口形状已确定** = **B 类**；门没过且**连接口语义都定不下来** = **C 类**。

| 门 | 判据 | 依据来源 |
| --- | --- | --- |
| G1 事实门 | 该能力依赖的现场事实（端口、接线、参数语义、阈值、协议）是否已确认 | 任务书 §2.2、§4.1 |
| G2 能力门 | 底层 `libs` 是否已提供该能力所需的设备入口 | `src\include\libs\devices\*.hpp` |
| G3 判据门 | 是否存在可验证的"做对了"的判据（应答、测试点、验收观察点） | 任务书 §8.2 |

### A / B / C 的含义

| 类别 | 含义 | 允许的代码形态 |
| --- | --- | --- |
| **A 现在可以放** | 三门全过 | 完整实现 + 离线测试 |
| **B 现在可以放骨架** | G1 或 G2 未过，但接口形状已由任务书/既有方案确定 | 接口、类型、状态枚举、不变量校验、`unavailable` 语义；**实现体留空或抛 `unsupported`** |
| **C 现在不能放** | 语义本身未定，或底层无对应驱动 | 只有一条 TODO 注释和一份前置条件清单 |

**A 类的共同特征**：判断依据完全来自软件内部或已解码的结构化数据，不需要任何新的现场标定。

**B 类的共同特征**：接口形状已经确定（任务书或既有方案已写明），但**实现所需的现场事实或标定值缺失**。
放骨架的价值是：让上层编排、UI、远程控制可以先跑通，且缺失事实被显式记录而不是被默认值掩盖。

> **C 类的红线**：C 类不是"暂时没空写"，而是"现在写出来的任何实现都是猜测"。
> 任务书 §5.2 对此有明确要求：算法未实现时**不得用 0、随机值、演示值或光谱强度填充为真实成分含量**。
> 这条原则对全部 C 类项目同样适用。

### A / B / C 现在是子项属性

一个业务能力**内部不同子项的成熟度可以不同**，这很正常：
能力 11「成分分析」既有可以立刻写的 B 类结果类型，也有只能留 TODO 的 C 类算法实现——
这两件事在现实中本来就是一件事的两面，强行拆成两行只会让落地顺序失真。

因此本文的记法是：**能力为行，子项带类别标记**（如 `11.1 [B]`）。

### 2.3 移出业务能力清单的 2 项

这两项**不是被删除，是被降级为跟踪项**——它们当前不构成"业务能力"，因此不应占据能力清单的行数。

| 原编号 | 项 | 移出去向 | 移出理由 |
| --- | --- | --- | --- |
| 24 | 传送带运行控制 | 外部前提假设 | 任务书 R02 仅说明"检测期间传送带持续运行"，是**外部前提而非本软件的控制对象**；驱动层亦无对应入口。既然不是控制对象，它就不是一条业务能力，而是一条**假设** |
| 26 | 光学窗口保护 | 暂不纳入范围 | 任务书 §6.1 明示"光学窗口保护**以后考虑**"，并要求**不引入**吹扫、快门、清洁机构等未确认需求。任务书既已明令不引入，留在范围表里就等于留了个假待办 |

**两者的后续处理不同，不要混为一谈**：

- **传送带**：需要一次**确认**（是否由本软件控制）。若确认"否"，业务层只保留"传送带运行中"这一状态前提假设，
  写入 `SiteConfig` 的使能开关与运行记录，不产生控制代码；若确认"是"，则**重新立项**并补 G2（补电机/继电器驱动）。
- **光学窗口保护**：**只等用户提出**。在此之前不得有任何相关设计痕迹——任务书 §6.1 的禁令是"不引入"，
  不是"不禁止"，所以它不进待办清单，只在本表留一行备忘。

### 3.3 参数管理与持久化

#### 3.3.1 参数管理骨架 `[A]`

| 项 | 内容 |
| --- | --- |
| 依据 | 任务书 §4.1–4.2：光谱仪/激光器/触发参数可设置可覆盖；**返回"参数设置已完成"**；运行中允许改参 |
| 可放的部分 | 参数分组结构、设置/覆盖/查询三个操作、**完成应答的两态语义**（收到请求 ≠ 设置完成）、核心参数"是否齐备"的判定 |
| 不可放的部分 | 各分组的**具体字段**（任务书 §4.1 明示"具体核心字段由后续接口细化"） |
| 形态 | `business/policy/` 或 `business/services/` 中的 `DetectionConfig`；缺字段时返回"未完成"而不是"完成" |

**"设置已完成"的语义是本子项的核心价值**：它把任务书 §4.2 的硬要求（失败不能返回成功应答）变成一个不变量，可以在没有硬件的情况下离线测。设备应用失败、校验失败、持久化失败三条路径都必须走"未完成"。

#### 3.3.2 断电保留与持久化 `[A]`

| 项 | 内容 |
| --- | --- |
| 依据 | 任务书 §4.2：参数需保存到持久存储，断电后可继续沿用 |
| 可放的部分 | 读写持久化、启动时加载、**"已保存的软件值"与"设备实际生效值"分开表达** |
| 不可放的部分 | 断电写入一致性规则（任务书 §4.3 明示待细化）——建议按"先落盘再应答"的保守策略实现，并在注释中标注该策略尚未确认 |
| 注意 | 读取到已保存参数 **不等于** 硬件已加载，更 **不等于** 上电自动发光或运动 |

#### 3.3.3 参数"生效时点"仲裁 `[B]`

| 项 | 内容 |
| --- | --- |
| 卡点 | 任务书 §3 步骤 7、§4.2：运行中改参的"生效时点及是否需要采集暂停尚未确定" |
| 可放 | 仲裁接口：`apply_at_next_idle()` / `apply_immediately()` 两种策略的**并存**，默认前者（保守） |
| 不可放 | 选定其中一种为业务规则 |
| 价值 | 两种策略同时存在时，采集期间不会被参数变更撕裂；后续确认后删掉一个即可 |

> **为什么这一项不单列为一个能力**：它不是一个模块，是参数模块内的一个函数。
> 原方案 §7 落地顺序的第 4 步本就写作"参数管理 + 持久化 + '设置已完成'两态应答"——三件事一步做完。
> 保留 B 类标记即可，不占能力行数。

| 安全默认参数 | 全部取协议量程下限：电流 15 A、脉宽 50 us、频率 1 Hz、放电延时 0 us、Q 延时 2 us、电压限值 0 V、Q 预热 0 s；Q 分频取 0（见下） |
| 触发方向 | **激光器触发光谱仪**，即 AvaSoft 手册 §4.9 的**接法二**：激光器 TTL 输出接光谱仪 **pin 6**，光谱仪跑外触发模式等这个脉冲，收到后再等积分延时才开始积分。默认配置 `wait_for_laser_trigger = true` |
| 换算关系（已确认，不再是猜） | 积分延时纳秒 → FPGA 计数 = `6.0 * (ns + 20.84) / 125.0`，反向 `ns = 125.0 * (计数 - 1) / 6.0`，逐字取自 SDK 示例 `qtdemo.cpp:462/975`。125/6 = 20.833 ns，即手册说的 21 ns 步进。激光延时/宽度**无**此偏置，两者不能混用 |
| 安全默认积分延时 | 5000 ns（5 us）。手册给的型号下限为 0.28 us（AvaSpec-3648-USB2）与 1.28 us（AvaSpec-2048-USB2），5 us 两者都满足；现场按样品标定 |
| 方向不得写反 | `control.laser_width` / `laser_delay` 在本流程**恒为 0**。那两栏是"光谱仪发 TTL 出去点火激光器"（接法一），一旦填非零就是方向反了，现场表现为**激光永远不出光、光谱仪一直等触发直到超时**。该约束由 `tests/test_spectrometer.cpp` 逐字节钉死 |
| 协议冲突（如实记录） | 协议 §3.1 标 Q 分频量程 1~10，§3.3 却写"0x34 单次触发，分频数为 0、Q 打开时有效"。单次触发要生效必须分频 0，故**按触发要求取 0 并覆盖量程表**。此决定已写进代码注释与日志，待与厂家核对 |
| 纪律 | ① 门禁是唯一判定入口，本服务不自己判断能否出光；② **门禁不放行时一帧写指令都不许发**（测试逐条钉死）；③ 失败必须中止到底，"发了"不等于"成了"；④ 收光/停机无条件执行，光闸绝不能留在开的状态；⑤ 半套参数不进 EEPROM |
| 离线验证 | `tests/test_laser_fire.cpp`，73 个断言，替身串口跑完整序列 |
| 触发相关离线验证 | `tests/test_spectrometer.cpp` 150 个断言，其中专测触发方向：FPGA 换算正反自洽、负延时被拒、延时无触发源时报 `delay_without_trigger`、外触发下 `laser_width`/`laser_delay` 必须为 0 |

**顺带修掉的三个真实缺陷**（前两个是门禁相关的，不是出光功能本身）：

| 缺陷 | 后果 | 修法 |
| --- | --- | --- |
| 门禁取的安全位**极性写反**：协议里 1 分别是"联锁断开/急停/过温/光闸开"，全是危险态，原代码按 `raw==1` 判为安全 | 真机联锁断开会被读成"安全"，门禁形同虚设 | 抽成公共函数 `policy::parse_actual_frame`，四处取反（`raw==0` 才安全），出光服务与门禁轮询共用同一处实现 |
| 解码层把过温位命名为 `overtemperature`，门禁找的是 `over_temperature`，查找永远落空 | 过温时该位保持默认值"安全"，**过温漏过门禁** | 统一为解码层的 `overtemperature` |
| 放电计数器（0xB2 data[13..16]，4 字节）被 `static_cast<uint16_t>` 截成 16 位 | 计数过 65535 回绕，表现为"出光确认说没出光"，极难查 | `Field` 增加 `raw32`/`wide` 与 `quantity32()` 工厂，让调用方没有机会截断；`parse_actual_frame` 取 `raw32` |

### 5.1 目录命名体系：采用 `config / policy / plan / session / services / app`

现存方案的命名体系（C++ 生态自然、依赖方向已在 CMake 中验证）胜出。落地目录为：

```text
src/
├─ business/
│  ├─ config/         端口表、站号、超时、设备使能开关（可加载，非硬编码）
│  ├─ policy/         出光门禁、联锁判读、就绪判定等规则
│  ├─ plan/           一次测量该做什么（时序方案）
│  ├─ session/        独占持有全部设备对象
│  ├─ services/       对外唯一门面
│  ├─ app/            进程生命周期、依赖装配、退出清理
│  ├─ data_delivery/  ★ 补入：本地保存 + 后续网关交付
│  ├─ logging/        ★ 补入：运行记录与事件日志
│  └─ simulation/     ★ 补入：模拟设备、离线流程演示
├─ businessd/         守护进程（命名管道 JSON 服务）
├─ remote/            Python CLI（不参与 C++ 构建）
└─ ui/                Qt6 Widgets（可选）
```

★ 三个补入目录对应任务书 §7.3 中已有、但现存方案未单列的部分。
`data_delivery/` 与 `logging/` 对应任务书 §6.3、§5.3；`simulation/` 对应任务书 §8.1 C 阶段的"模拟设备、离线流程演示"要求。

**任务书 §7.3 名词的翻译表**（供读旧文档时对照）：

| 任务书 §7.3 | 本方案落点 | 说明 |
| --- | --- | --- |
| `configuration/` | `business/config/` | 一一对应 |
| `units/`（位置、物料、采集、环境、恢复、指示） | `business/policy/`（规则）+ `business/plan/`（时序） | 拆为两半 |
| `app/` | `business/app/` | 一一对应 |
| `adapters/`（8 个设备） | `business/session/`（持有）+ 驱动层 `libs_devices` | **适配器已存在，不新建** |
| `domain/` | `business/plan/` + `services/` 的类型定义 | 分散定义 |
| `interfaces/` | `business/services/` 门面 | 一一对应 |
| `data_delivery/` `logging/` `simulation/` | 同名补入 | 见上 |

**关于 `units/` 一行的补充**：任务书把"指示"（状态灯）与"环境"（空调）并列为两个 unit，
本报告把它们分别并入能力 4 与能力 9。这不改变翻译表本身——翻译表讲的是**目录落点**，
能力划分讲的是**判定单元**，两者不必一一对齐。

**`adapters/` 一行值得单独强调**：任务书写的是"新建 8 个适配器"，但 `libs_devices` 已经实现了其中 5 类
（激光 / 测距 / 光谱 / 空调 / 指示灯），另 2 类（网关 / 电机）待建。业务层再建一套就是重复实现。
**设备适配器的归属不变：仍在驱动层**，业务层只在 `session/` 里持有它们。

### 5.2 进程模型：采用守护进程 + 薄客户端

现存方案 §7.4 的形态胜出：**C++ 守护进程独占设备 + Python CLI 经命名管道 JSON 通信**。
任务书 §7.3 的"单进程 + 多模块"视为 C 阶段早期草案，**实施时直接按守护进程形态编写**。

这条裁决的实际影响，比看上去大：

- **不写"阶段 C 用单进程、阶段 D 再改守护进程"这条路径。** 因为独占性约束在离线阶段同样成立
  （`serial.cpp` share=0、AvaSpec 命名互斥体、SSH 断开会杀掉远端子进程），
  单进程版本到现场必然要重写一遍 `services/`。
- `services/` 从第一天起就是**跨进程可调用**的：入参出参都是可序列化的值类型，不持有裸句柄。
- 本报告 §6 落地顺序里的第 9 步（守护进程 + 多客户端）因此不是"D 阶段的事"，而是**与前 8 步同期推进**。

## 7. 三条贯穿全部类别的纪律

1. **区分"事实"与"意图"。** 驱动给事实（`interlock_1` 的值），业务给判断（因此禁止出光）。
   任务书 §2.2 反复区分"开始检测业务信号"与"物理触发"，§6.2 反复区分"恢复上下文"与"重发命令"——
   这类区分必须落到类型层面，不能只写在注释里。

2. **未知 ≠ 正常。** 空调通信失败、测距超量程、光谱通道缺失、算法未实现——
   全部要有独立于"正常/异常"的第三态。任务书 §5.2、§6.1 已明确要求，实现时必须照办。

3. **占位值必须带标记。** 运动时间 1 s、距离 3–5 cm、频率空值——
   任何出现在输出、日志、上报中的占位值都要能被识别为"未标定"。
   任务书 §8.2 已把"占位与标定值可辨别"列为验收观察点。

> **合并后新增的一条实施纪律**（不新增原则，只固定边界）：
> 一个能力内部的不同子项**不得互相代偿**。
> 具体地：3.4.2 出光门禁不得替 3.9.2 空调联锁下判断；3.10.1 采集协调不得替 3.11.2 算法填结果；
> 3.12.1 的占位行程时间不得被当成 3.12.2 的电机已可用的证据。
> 合并的是**归属**，不是**成熟度**。
